Sequencing (Brian ruled in chat, 2026-11-25): the int-id code can't read a
TEXT id, so this ticket ships the migration as a named `uuidMigration` SQL
string next to `migrations`, without appending it. ti-1034 appends it when the
code switches to string ids. Until then the tests apply it directly to a seeded
database.

`uuidMigration`, one SQL script that runs inside applyMigration's transaction:
- `ticket_uuids(legacy_id, id)` maps every integer id that appears anywhere
  (tickets, parent_id, deps, events, jev) to a UUIDv4 built from
  `randomblob`. Removed tickets' history keeps one id per ticket that way.
- Rebuild tickets (`id TEXT PRIMARY KEY NOT NULL`, `legacy_id INTEGER UNIQUE`,
  `parent_id TEXT`), ticket_dependencies, ticket_events, and jev_evaluations
  with TEXT ticket columns, copying through the map. Recreate their indexes
  and the ticket_events append-only triggers. Rewrite `closed_by` in done
  event data with json_set. Event and jev rows keep their own AUTOINCREMENT
  ids.
- Dropping the old tickets table removes its sqlite_sequence row. Drop the
  temporary map at the end.

Reorder stores only order_rank, so it has no references to rewrite.

Ordering: queries that order or tie-break tickets by `id` switch to
`created_at, id` (commands.go deps, in-progress, stale, plan concepts;
stats.go plan concepts). Event-id ordering stays.
